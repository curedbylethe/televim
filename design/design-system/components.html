televim — component specimen

Seven components, each on a fixed 80×24 grid. Colours come from tokens.css; the sheet itself is not part of any frame. Every frame is generated from televim-engine.js by design-system/build-specimen.js, so the sheet cannot drift from the engine.

  1. Four real screens, stacked.   1. The cue. One column, dim, present, on the row it belongs to and blank on a wrapped row’s continuation: the device the conversation already uses for `[you]`/`[them]`, in one cell instead of a word. Both cards use it, action rows included.
  2. The selection row is reverse video, as a message’s is, and the normal caret on it is the ground colour so it can be seen against that reverse. A cursor that moves inside a row and cannot be seen is a cursor nobody knows the position of.
  3. A row exists only when the peer says something. `birthday`, `bio` and `username` are absent, never empty, which is why a contact’s card is often shorter than the self card. The title’s `(n/m)` counts what the peer gave.
  4. The self card ends the same way a message does: its two action rows are dim, they refuse, and `logout` raises a screen-wide confirmation and refuses inside it. The refusal replaces the prompt, because a confirmation outranks a transient status and both are the same row.
  5. One row is reserved and not designed: the colour slot, held between the name and the username. It draws nothing, and the constraints it will have to satisfy are in DESIGN.md.

↑ the card, no inline position · keys Sjjjjj · mode NORMAL

  1. Four states, one rule. A read-only surface marks its cursor with reverse video on the row itself — the selection row — and nothing else is reversed. A caret drawn inside that row takes the ground colour, because the row's own reverse would hide it. A caret on a plain ground takes --text.
  2. The two carets have two names. The insert caret is the two-column bar, drawn while the line is being composed; the normal caret is a hollow cell, drawn for the line's own Normal mode and for a card's inline position. Both are painted. A terminal cursor is a single shape the program cannot change by mode, which is exactly the thing the two names exist to separate.
  3. The bar's ink and the hollow's ink are one rule, not two colours. On a plain ground both are --text; on the selection row both are --background. The two carets differ in shape, never in ink.
  4. The fourth frame is the pair to the third. The inline position is drawn only on a value row, so the card on its add account row — an action row — is the selection row with no caret on it. The two frames are the same treatment with and without the caret, which is what makes the third state legible. The one other card state that inks a caret on a surface that is not reversed is a charwise selection: the row is then the selection background rather than reverse video, and the hollow takes --text there, by the same rule.
  5. The names are the port list. Theme::selection is kept; Theme::caret_insert and Theme::caret_normal are added. The engine's flags are r, c and n; the classes .rv, .ci and .cn.

↑ Esc, then :unlock asks again · keys <Esc>:unlock<CR> · mode INSERT

  1. One sentence says what is asked and why. The file is encrypted and no key is available, so televim needs the passphrase to read its chats. It is the box's first line, plain, in the sign-in view's voice; nothing else in the box explains the question.
  2. The bar is the sign-in bar. Titled Passphrase, and concealed as bullets, one per character, with no echo of the text. It takes the same keys as the sign-in password: typing, ⏎ to send, Esc to leave. A passphrase has no Normal mode, because a Normal-mode key could move a secret into view.
  3. The list stays, and says it is a cache. While locked the chat list is the local cache, and its title carries the title note · cached. The box is drawn over the right column only, so the two panes keep their widths; an empty list reads Chats (0) with no note, because nothing is cached.
  4. Checking is the sign-in's word. Checking… in the box and on the bar's status, a first ⏎ refused with a flash and a second doing nothing. The key is derived in the background and the answer lands on its own.
  5. A refusal stays. It is the box's line, not a flash, so it is still there when the reader looks up from the bar. It names the file as left alone: that passphrase did not open the session file; the file was left as it was.
  6. Esc leaves the reader where they were. The box goes and the focus returns to the pane it came from. The session stays locked, and the status says so: the session stays locked — :unlock asks again. :unlock is the proposed route back in, and on an open session it is refused.
  7. The demo passphrase is lantern. A demo-only rule, so every frame is reproducible. Anything else is the wrong one.

  1. The confirmation is the quit row's widget. Change the session passphrase? (y/n) sits on the status row at the confirmation's rank, and n or Esc leaves the file untouched. Nothing is asked for until y.
  2. The new passphrase is entered twice. A repeat is asked because a typo here would lock the file under a key nobody can recall, and nothing else holds the key. Both entries are concealed. The box says so in one sentence and says that the second one is coming.
  3. A repeat that differs changes nothing. The box says the two entries differ, so nothing was changed and the file was left as it was, and the new passphrase is asked again from the start.
  4. Success says what changed, then what to update. The status row carries Session passphrase changed.; the box carries the reminder: if the old passphrase was set in TELEVIM_SESSION_PASSPHRASE or in the config file as session_passphrase, update it to the new one, or the next launch will not open the file.
  5. Failure says the file is as it was. Session passphrase not changed: the file was left as it was. The box names the reason and says the old passphrase still opens the file. The demo fails any new passphrase beginning with !, the same convention as the failed search.
  6. A locked session cannot be changed. :passphrase is refused with the session is locked: :unlock first. :passphrase and :unlock are proposed in this spec and are not in the shipped command set yet.
