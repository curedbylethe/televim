Televim — baseline mockups

Six frames of the screens that exist today, at exactly 80 columns by 24 rows. They are the reference the settings work in plans 03, 04 and 05 is measured against, and they are hand-written rather than generated: a mockup produced by the same process as the spec cannot contradict the spec, which is the one thing a reference frame has to be able to do.

Every string on them is copied out of crates/ rather than invented — the nine hint rows from input_bar.rs, the bracket vocabulary from rows.rs, the titles and the note joins from chat_list.rs and conversation.rs. The colours are the v2 column of DESIGN.md's palette, which the binary does not draw yet.

  • Conversation, Normal mode The reference frame. Focused border, both titles, the scrollbar's own column, the hint row.
  • Two messages selected Selection as a background across whole rows; reverse video still only the cursor's.
  • A confirmation The label outranks the focus, the hint is gone, and the prompt names which side.
  • Composing The bar grown to two rows, · for every space, Message to … rather than Message.
  • A search hit under the cursor Match is a foreground, selection is a background, one cell is both.
  • The reference frame, light terminal The same frame with the light column — and the one value that fails a body-text ratio, deliberately.

What is not here yet

A settings panel, an editable profile, and an interactive sign-in with 2FA. Each of those is work that does not exist in the code yet, and each brings its own mockups in this style. The settings panel takes the conversation's rectangle rather than a new pane, so a contact profile will land in the same slot later.

What each one is for

Each mockup carries its own TestBackend assertion list — the checks that would catch it regressing, written before the code exists. That is the point of a reference frame: it is not a picture of a screen, it is a statement about what the screen must be true, expressed as something a test can read off a buffer.
